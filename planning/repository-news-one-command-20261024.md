## 2. 推荐结构

官方原文/行情 → 无发送能力的采集器 → 仓库证据与八时点资料包 → 既有只读资料接口 → GPT统一任务入口 → 五Skill候选 → 用户核对采用 → 剧情/已用新闻/人物记忆更新。

仓库保存长期版本和证据；已有共享进度保存当前任务/草稿/用户更正。向私有GPT提供短资料包，避免一次返回整仓库、重复读大JSON和多工具大回复。

第一阶段复用现有接口：GitHub采集完成、资料包提交并读回后，向已有Cloudflare资料服务同步同一资料包，保留仓库路径、commit SHA和内容hash。GPT继续调用现有getNewsPacket，不再另开Google OAuth或要求GPT直接拿GitHub写入令牌。同步失败时仍保留仓库包，接口明确不可用/版本落后；不能拿旧缓存当当天已更新。

GitHub→接口写入建议用专用、仅允许新闻入库的凭据，不给它修改工作进度/人物/规则的权限；凭据只在GitHub Secret与服务Secret保存。该接入需要实施时另行明确授权及端到端测试，本设计不创建凭据。

## 3. 仓库资料设计

- 保留现有 `news/editions/` 采集记录，不删除或覆盖历史。
- 新增 `news/packs/YYYY-MM-DD/HHmm.json`：每个罗马尼亚日期/时点一份面向GPT的短资料包；修订有版本与来源hash。
- 新增 `news/pack-index.json`：只列日期、时点、包路径/版本、生成时间、覆盖情况、审核状态、行情状态、有效截止时间；不把海量正文堆进index。
- 新闻正文以结构化事实、必要短摘录、官方原文链接、发布时间/事件时间/采集时间及证据hash为主。大附件按需读取，避免把每次全量抓取正文重复提交到主分支。后续新增临时产物可设保留期，但不擅删既有档案。
- 每条新闻保留event_id；同事件无实质新增不再推荐；有新进展保留delta与前版链接。只有用户采用后才写“已用于正式剧情”，候选只能记“已提议”。
- 行情独立字段：指标/代码、交易所、交易日、数值、前收、点数和百分比变化、币种、报价时间、延迟、开盘/盘中/休市状态、来源。缺数据就保留缺项，不让新闻解释补造报价。
- 资料状态区分RAW_CAPTURED、STRUCTURE_CHECKED、READY_FOR_GPT_REVIEW、EDITOR_VERIFIED、CANDIDATE、ADOPTED；原始采集成功不自动提升为EDITOR_VERIFIED。

## 4. 八个时点与时间规则

统一Europe/Bucharest，沿用用户已定时点，不新建重复任务：

| 时点 | 备料目标 |
|---|---|
|08:30|前一交易日美股收盘指标＋1—3条重要新闻；注明实际交易日|
|10:05|BVB开盘数据与当时实际交易状态|
|10:30|1—2条国际财经新闻，罗马尼亚相关优先|
|14:00|1—2条有实质新增的新闻|
|15:00|1—2条有实质新增的新闻|
|16:00|1—2条有实质新增的新闻|
|16:30|美股指标与实际交易状态；核对纽约09:30及夏令时错位|
|17:00|1—2条有实质新增的新闻|

08:30/新闻包可提前备料后在时点复核；开盘数据须在真实开盘后获取，不能用提前抓取数据冒充开盘报价。非交易日包仍明确写休市和最近行情日期。新闻可每天备料，群聊日程仍按工作日/周末规则区分。

GitHub Actions支持IANA timezone，但schedule可能延迟，不承诺秒级准点。每包保留scheduled_for和实际captured_at；迟到时真实注明。小时采集覆盖与八时点整理分开，不能只查最近一小时导致早报漏掉隔夜重要事件；需要配置新闻窗口和持续事件的新增判断。

## 5. 一句话任务路由

目标：用户只说意图，系统从当前日期/故事时间、已采用进度、现行规则、资料包和人物证据补齐其余信息；只问缺少且影响正确性的关键问题。默认不反复询问已确认人数、条数、标签、姓名格式和固定课表。

| 用户说法 | 系统判定及动作 | 默认数量 |
|---|---|---|
|开上午群/开下午群/开晚群|读用户更正、源文末句、场次已采用数与相关新闻包；避免重复开场|补至本场35条，含助理先生；整场从零才35条|
|继续|读最近已采用末句与未采用草稿，确定延续哪一个；不把草稿转正|补当前剩余额度；已满不硬续|
|发资讯/整理资讯|识别用户指定时点，否则使用当前已到时点最新有效包；核对原文和已覆盖事件|按八时点1—2条或早间1—3条；无新增明确说明|
|按14号改这句/粘贴编号对白|轻量口吻改写，只加载该人身份与原话，不跑全天新闻流程|仅输入范围，不扩写整场|
|检查今天|核对各场35条、空标签、编号性别、重复、人物与上下文矛盾；给原文位置|逐项问题清单，不强行重写全文|
|采用这版|确认本轮具体版本后归档正式文本、最后一句、已用事件和人物状态；保留草稿版本|只采用用户明确指向的版本|
|记住这条规则|保存用户原话、适用范围和生效版本，读回确认|只保存相关长期规则，不把单次安排扩大为永久规则|

“发资讯”默认交付可复制候选，不发送Telegram/WhatsApp；“采用”不等于发送或现实成交。系统可自行决定有依据的选角、话轮和表达，不能自行编造新闻、人物往事、持仓或批准稿件。

中期可把读取步骤收敛为getWorkContext(intent,date,session)返回任务合同（目标/剩余条数/来源版本/相关人物/新闻包/未答问题），生成后由validateDraft检查编号性别、空标签和计数，语义审稿仍由GPT与用户核对。接口尚未实现，不在指令中假装已存在。

## 6. 按时入库与GPT自动醒来必须分开

先实现“按时备好资料，用户一句话自动取用”的可靠链路。普通私有GPT的Action是工具接口，不因为仓库到点更新就自动醒来。

如需到点主动备稿/提醒，逐一检查既有8个ChatGPT定时任务是否能在该运行环境使用仓库或资料接口，并验证真实运行、写回与投递位置；能用则复用原任务，不能用则说明限制，不创建一套假装互通的任务。不会承诺投递到任意独立聊天窗口。此设计不启用任何任务。

## 7. 实施顺序和验收

1. 保留旧发送器停用状态，新建不加载Telegram凭据的“新闻资料入库”入口。先修复来源失败并检查隔夜窗口与RO/US覆盖。
2. 实现短资料包及固定八时点索引，独立接入行情。测试旧闻、无新增、休市、夏令时错位、数据延迟、缺来源、抓取不完整和并发提交。
3. 只接通一个时点的“原始来源→仓库包→资料接口→私有GPT真实取用”链路，读回commit/hash/时间；Telegram发送数必须为0。
4. 用“开上午群、继续、按编号改写、检查、采用”分别验收目标识别、35条补额、身份、上下文与保存回执，再扩展其余时点。
5. 最后单独验收定时GPT运行；无法验证时只交付已验收的按时入库＋按需读取，不宣称全自动备稿。
